# Delhivery Last-Mile Delay Intelligence Pipeline

A single, connected pipeline that answers three operational questions for a
regional operations team:

1. **How long will a parcel take?** — a `delivery_hours` regression (Part B).
2. **Will a parcel miss its promise?** — a delay classifier with an alert
   threshold tuned to the operations rule (Part C).
3. **Which hubs need which playbook?** — K-Means hub segments and a tier-label
   audit, combined with the classifier into a concrete action list (Part D).

The cleaning and feature code written in Part A (`src/shipment_prep.py`) feeds
every later Part, and the same two functions are reused by the scoring script so
training and prediction preprocess data identically. The data is **synthetic**
and produced by `generate_data.py`; no real shipment records are used.

Reference numbers in this README were produced with the pinned configuration
(`random_state=42` throughout) and verified against the output CSVs in
`outputs/` and `models/`.

## How to run

From a fresh clone, run these commands in order from the repository root. Each
script reads only files already in the repository and writes its outputs before
the next script needs them.

```bash
pip install -r requirements.txt
python generate_data.py            # prints: 24 1224 48
python part_a_clean_eda.py         # writes data/modelling_table.csv + outputs/part_a_*.csv
python part_b_regression.py        # writes outputs/part_b_*.csv
python part_c_classification.py    # writes outputs/part_c_*.csv
python part_d_segments.py          # writes outputs/hub_*.csv, segment_profile.csv, part_d_separation.csv
python package_model.py            # writes models/* and outputs/part_d_reload_check.csv
python predict_delay.py            # writes outputs/new_shipment_actions.csv
```

`models/delay_model.pkl` is **regenerated by running `python package_model.py`**.
A pickled scikit-learn model loads reliably only on the scikit-learn version it
was written with (`requirements.txt` pins it). If a grader's installed versions
differ, they should re-run `package_model.py` instead of loading the committed
pickle; `package_model.py` rebuilds the exact same pipeline deterministically.

`requirements.txt` pins the four libraries with `==` (`pandas`, `numpy`,
`scikit-learn`, `joblib`) to the versions used here.

## Data findings

All figures below are read from `outputs/part_a_delay_by_group.csv`,
`outputs/part_a_correlations.csv`, and `outputs/part_a_checks.csv`. Overall,
278 of 1,200 parcels are delayed (delay rate **0.2317**).

- **Service type.** Express parcels miss their promise most often, at a delay
  rate of **0.4897** — far above Standard (**0.2056**) and Economy (**0.0857**).
  Express has the tightest promise (36 hours), so the same real transit time
  breaches it most easily.
- **Hub tier.** Delay rate climbs steeply from Tier 1 to Tier 3:
  **0.0400 → 0.2150 → 0.4400**. A Tier 3 parcel is roughly eleven times more
  likely to be late than a Tier 1 parcel.
- **Distance band.** Delay rate rises monotonically with distance:
  **0.0219** (0–200 km) → **0.1368** (201–400) → **0.4364** (401–600) →
  **0.8523** (601+). Beyond 600 km, most parcels are late.
- **Strongest drivers of `delivery_hours`.** Ranking the columns of
  `part_a_correlations.csv` by absolute correlation (excluding `delivery_hours`
  itself), the top three are `promised_hours` (**0.8372**), `distance_km`
  (**0.4013**), and `n_stops` (**0.3247**). Transit time is driven mostly by the
  service class and the physical lane, not by the bookkeeping columns.
- **Why log-transform `declared_value_inr`.** On the median-filled column the
  mean (**1533.05**) sits far above the median (**1121.5**), the signature of a
  right-skewed, long-tailed variable. After the natural log the mean (**7.028**)
  and median (**7.022**) almost coincide, so `log_declared_value` is a better
  behaved model input than the raw rupee amount.

## Model results (regression)

Source files: `outputs/part_b_metrics.csv`, `part_b_tree_depth.csv`,
`part_b_gb_learning_rate.csv`, `part_b_cv.csv`, `part_b_checks.csv`. The split is
840 / 180 / 180, and the scaler is fitted on the 840 training rows only
(`train_scaled_max_abs_mean` ≈ 0 while `test_scaled_max_abs_mean` ≈ 0.2187,
confirming no leakage).

- **Baseline.** Predicting the training mean for every parcel gives R²
  **−0.0212** on validation — essentially zero explanatory power, the floor any
  real model must beat.
- **Winning model.** Linear regression had the lowest validation RMSE
  (**4.8912** hours), edging out gradient boosting (4.9165), random forest
  (5.4680), and the depth-6 tree (6.2796). Scored once on the untouched test
  set it reaches R² **0.9493** (RMSE 4.5235 hours) — delivery time is largely
  linear in these features, so the simplest model generalises best here.
- **Bias vs variance (tree depth).** Depth 1 is **high bias**: train and
  validation RMSE are both high and close (11.6334 vs 12.1324, a gap of only
  ~0.50). An unlimited tree is **high variance**: it memorises the training rows
  (train RMSE **0.00**) while validation RMSE stays at 7.79 — a gap of ~7.79.
  Validation RMSE is lowest at depth **6** (6.2796).
- **Learning rate.** Validation R² is **0.7127** at 0.01, **0.9306** at 0.1, and
  **0.8440** at 1.0. 0.1 is best; 0.01 is too slow (100 trees cannot catch up),
  and 1.0 overshoots (each step over-corrects and the ensemble becomes unstable).
- **Cross-validation.** On the 1,020 train+validation rows with a shared
  `KFold(5, shuffle=True, random_state=42)`, gradient boosting has the higher
  mean R² (**0.9352**, std 0.0044) versus linear regression (**0.9261**, std
  0.0048). The two rankings disagree slightly: linear regression wins on the
  single validation split, but gradient boosting is marginally stronger and more
  stable across folds. Because the test-set gap is small and linear regression is
  cheaper and more interpretable, I would ship **linear regression** and keep
  gradient boosting as the documented fallback.

## Model results (classification)

Source files: `outputs/part_c_models.csv`, `part_c_feature_scores.csv`,
`part_c_selectk.csv`, `part_c_tuning.csv`, `part_c_thresholds.csv`,
`part_c_final_test.csv`, `part_c_final_config.csv`. The stratified split is
840 / 180 / 180 with 195 / 42 / 41 delayed parcels.

- **Why accuracy alone is useless.** The blind "always on-time" baseline scores
  accuracy **0.7667** simply because ~77% of parcels are on time — yet it catches
  **zero** delays (recall 0, TP 0). Accuracy hides a completely useless model, so
  the project optimises recall/precision instead.
- **Noise columns carry no signal.** The five bookkeeping columns
  (`label_print_batch`, `scanner_build_no`, `tape_roll_no`, `sticker_serial_mod`,
  `shelf_slot_no`) together account for only about **0.225** of the forest's
  importance (the five `is_noise` rows of `part_c_feature_scores.csv`), and all
  five fall outside the top 7 by F-score (each `f_rank ≥ 8`, each F-score below
  10, versus a smallest top-7 F-score of 36.73). Dropping to the top **7**
  features loses nothing.
- **How many features.** `part_c_selectk.csv` shows validation F1 peaking at
  **k = 7** (**0.8333**), above k = 5 (0.6988), 10 (0.7857), 12 (0.8049), and 17
  (0.7848). Seven features is both the best and the most parsimonious choice.
- **Did tuning help?** On validation, the untuned forest on the same 7 features
  (`val_f1` **0.8333**) actually beat both `GridSearchCV` (**0.775**) and
  `RandomizedSearchCV` (**0.7848**), even though the grid's cross-validated
  accuracy (0.8952) was the highest. This is a caution about tuning against a
  180-row validation set: the F1 differences are within noise, and the grid's
  depth-capped best model is slightly more conservative. The final configuration
  therefore follows the tie-break rule and ships the **untuned 7-feature forest**.
- **Alert threshold.** Following the operations rule — the highest threshold
  whose validation recall is still ≥ 0.80 — the chosen threshold is **0.5**
  (`part_c_final_config.csv`). At 0.5 the validation precision is **0.7955** and
  recall **0.8333**; raising it to 0.6 would push recall to 0.7619 (below 0.80),
  so 0.5 is the correct cut. This deliberately favours recall, because a missed
  delayed parcel costs more than an unnecessary call.
- **Test performance (scored once).** At threshold 0.5 the held-out test gives
  precision **0.6889**, recall **0.7561**, and F1 **0.7209**. Test recall
  (0.756) is honestly a little below validation recall (0.833): the test set has
  only 41 delayed parcels, so a handful of misses moves the number noticeably.
  Roughly **7 of every 10 flagged** parcels are genuinely delayed, and about
  **8 of every 10 delayed** parcels are caught.

## Operations recommendation

For the regional operations head (sources: `outputs/hub_segments.csv`,
`hub_profile.csv`, `tier_vs_segment_mismatch.csv`, `part_c_final_test.csv`,
`new_shipment_actions.csv`, `part_d_separation.csv`).

- **The Escalate segment (9 hubs) needs the heavy playbook.** Ranked by delay
  rate: Guwahati HUB19 (**0.62**), Agartala HUB24 (**0.54**), Raipur HUB20
  (**0.48**), Nagpur HUB13 (**0.46**), Patna HUB17 (**0.46**), Siliguri HUB23
  (**0.44**), Bhubaneswar HUB21 (**0.40**), Ranchi HUB18 (**0.38**), and Kochi
  HUB15 (**0.36**). These carry the segment mean delay rate of **0.4600**.
- **Four hubs are mislabelled by tier** (`tier_vs_segment_mismatch.csv`) and
  their tier labels should not be trusted for staffing or promises:
  - **HUB07 Kolkata** — labelled Tier 1 but behaves like **Watch**; treat it as
    a regional hub, not a metro.
  - **HUB13 Nagpur** and **HUB15 Kochi** — labelled Tier 2 but behave like
    **Escalate**; give them the Escalate playbook despite their tier.
  - **HUB22 Dehradun** — labelled Tier 3 but behaves like **Watch**; it is doing
    better than its tier implies.
- **Alert economics.** At the shipped threshold (0.5), test precision is
  **0.689** and recall **0.756**: about **7 of every 10 flagged** parcels really
  are delayed (so ~3 calls in 10 are unnecessary), and about **8 of every 10
  delayed** parcels are caught before they are late. Given that a missed delay
  costs more than a courtesy call, this recall-leaning balance is the right one.
- **New batch.** Of the 48 incoming parcels (`new_shipment_actions.csv`),
  **8 were flagged**; of those, **6 need a hub-manager escalation** (flagged and
  in an Escalate hub) and **2 get a proactive customer call**. The other 40 need
  no action.
- **Why keep K = 3.** `part_d_separation.csv` shows the across-to-within
  separation ratio keeps rising (2.894 at K=2, **5.393** at K=3, 6.305 at K=4,
  6.887 at K=5), so a purely numeric reading would push K higher. But K=4 and
  K=5 each carve off a cluster of fewer than 6 hubs (K=4's smallest is 4 hubs,
  K=5's smallest is 2) — too small to justify its own operational playbook.
  K=3 (sizes **9-8-7**) is the largest K where every segment is big enough to
  staff and run, which is exactly what operations needs (three playbooks).

## Production plan

### Production-readiness mapping

| Characteristic | Where it lives in this repo |
|---|---|
| **Reproducibility** | `requirements.txt` pins exact versions; every split, model, and search uses `random_state=42`; `generate_data.py` is committed verbatim. |
| **Consistency** | `src/shipment_prep.py` defines `clean_shipments`/`build_features` once; both `part_a_clean_eda.py` (training) and `predict_delay.py` (prediction) import them, so preprocessing cannot drift between train and serve. |
| **Reliability** | `models/impute_values.csv` stores the training medians, so new parcels with gaps are filled deterministically and never crash scoring; `part_d_reload_check.csv` proves the saved pickle reloads with `reload_max_abs_probability_diff = 0.0`. |
| **Maintainability** | One script per Part, one shared module, and self-describing CSVs in `outputs/`; re-running a Part rewrites only its own files. |
| **Performance (speed)** | The served model is a `SelectKBest(7)` + 100-tree forest; it scores the 48-parcel batch effectively instantly and `predict_delay.py` is fully deterministic. |
| **Monitorability** | Every decision is written to an auditable CSV (`new_shipment_actions.csv`, `part_c_final_test.csv`), making drift and performance measurable week to week. |

### What to monitor (with triggers)

1. **Weekly delayed share of delivered parcels** — baseline **0.2317**. Trigger
   an investigation / retrain if it exceeds **0.28** for two consecutive weeks.
2. **Weekly share of parcels flagged** — on the latest batch ~**0.17** (8/48).
   Trigger if the flagged share drifts outside **[0.12, 0.35]**, which usually
   means the input distribution or the model's calibration has shifted.
3. **Recall on parcels whose outcome is now known** — target around test recall
   **0.756**. Trigger a retrain if measured recall falls below **0.60**.
4. **Precision on flagged parcels** — target around test precision **0.689**.
   Trigger a review if it falls below **0.50** (too many wasted calls).

### Retraining schedule and drift

- **Cadence.** Retrain monthly on a rolling window, and immediately whenever any
  monitor above fires its trigger.
- **The sale window.** The 15–28 September sale (`sale_event_flag = 1`) inflates
  delivery hours (and Express delays especially). When evaluating or retraining,
  compare sale weeks against the **same kind of event** (prior sale windows),
  never against ordinary weeks, or the model will look falsely degraded during
  every sale.
- **What drift looks like here.** A hub's per-lane `distance_km` / `n_stops`
  distribution shifting, a hub's true operating behaviour diverging from its tier
  label (exactly the HUB07/HUB13/HUB15/HUB22 situation), or the overall delay
  rate climbing above its 0.2317 baseline. Any of these means the stored medians,
  segments, and threshold should be recomputed.

## Limitations

- **Synthetic data.** Every row comes from `generate_data.py`; real Delhivery
  operations would have messier, correlated, and seasonal patterns this generator
  does not reproduce, so absolute numbers should be re-validated on real data.
- **Small positive test set.** The test set holds only **41 delayed parcels**, so
  test precision/recall/F1 (0.689 / 0.756 / 0.721) carry real sampling noise; a
  few parcels moving changes the third decimal.
- **Single-split threshold.** The alert threshold (0.5) was chosen on one
  180-row validation split (42 delayed). A production system should set the
  threshold with cross-validation or a cost model rather than one split.
- **Bookkeeping features retained.** The five noise columns are kept as inputs
  for honesty about the raw feed; `SelectKBest(7)` drops them, but a cleaner
  upstream feed would remove them before modelling.
- **Fixed K = 3.** Three segments are a business constraint (three playbooks),
  not a purely data-driven optimum; the separation ratio keeps rising for larger
  K, which the Operations section addresses explicitly.
